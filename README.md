# GeoRoute

**Intelligent Geographic Route Optimization and Algorithm Benchmarking Platform**

GeoRoute is a CS2009 semester project that turns classic design-and-analysis-of-algorithms concepts into a working, map-based application. It compares brute force and divide-and-conquer closest-pair algorithms, and compares an exact TSP solver with nearest-neighbour and 2-Opt heuristics on geographic cost matrices.

The project combines:

- a **C++17 native engine** for the algorithms and timing,
- a **Python FastAPI** backend for validation, geographic preparation, OSRM integration and reporting,
- a **Next.js + TypeScript** dashboard with **Leaflet** maps and **Recharts** benchmark charts.

> Academic note: straight-line and road-network costs are kept separate. A heuristic route is never labelled globally optimal. Optimality gap is reported only when an exact solution exists for the same matrix.

---

## Features

| Area | What is implemented |
| --- | --- |
| Locations | Click-to-add map markers, remove markers, choose depot, CSV import, deterministic synthetic Karachi datasets |
| Closest pair | Brute force `O(n²)` and divide and conquer `O(n log n)` on UTM-projected coordinates |
| Route optimization | Exact fixed-depot TSP for small instances, nearest neighbour `O(n²)`, optional 2-Opt local search |
| Distance models | Haversine great-circle, OSRM road distance, OSRM road duration, client-provided symmetric matrix |
| Benchmarking | Repeated runs, median/mean/min/max runtime, operation counters, scalability charts, optimality gaps |
| Reliability | Input guards, exact-solver limits, OSRM request limits, explicit service failures, clear error messages |
| Reporting | CSV, Markdown and JSON downloads generated by the backend |
| Visualization | Interactive Leaflet map, closest-pair highlighting, road or straight-segment route overlays |

## Architecture

```text
Next.js / TypeScript
  ├─ Leaflet map: add, remove, select depot, visualize pair/route
  ├─ Recharts: runtime, operation and cost comparisons
  └─ API client: typed JSON requests
        │
        ▼
FastAPI backend
  ├─ validation + dataset store
  ├─ UTM projection / Haversine matrices
  ├─ OSRM table + route geometry client with cache
  ├─ benchmark orchestration + report export
  └─ ctypes binding to the native engine
        │
        ▼
C++17 engine
  ├─ closest pair: brute force + divide and conquer
  ├─ TSP: exact + nearest neighbour + 2-Opt
  └─ high-resolution timers and operation counters
```

The backend loads `backend/app/native/georoute_engine.dll` (or `libgeoroute_engine.so` on Linux/macOS). If the native library is missing, a clearly labelled Python reference engine is used as a fallback so the dashboard still works; `GET /api/health` reports the active mode.

## Prerequisites

- **Python 3.10+** (tested with 3.13)
- **Node.js 20+** and npm (tested with Node 24)
- **C++17 compiler** (tested with MSYS2 `g++` 16 on Windows; GCC/Clang on Linux/macOS)
- Internet access for OpenStreetMap tiles and the public OSRM demo service. The app still works with straight-line or precomputed matrices when OSRM is unavailable.

## Quick start

### 1. Build the native engine

Windows (PowerShell):

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build-engine.ps1
```

Linux / macOS:

```bash
bash scripts/build-engine.sh
```

The script compiles a versioned shared library into `backend/app/native/`, writes `active.txt` to identify the current build, and runs the C++ unit tests. On Windows it also copies the small `libwinpthread-1.dll` runtime next to the engine. Versioned output means a rebuild works even while a backend process still has the previous library loaded; restart the backend to use the new build.

### 2. Install backend dependencies

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements.txt
```

### 3. Start the backend

```powershell
cd backend
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

### 4. Start the frontend

In a second terminal:

```powershell
cd frontend
npm install
npm run dev
```

Open **http://localhost:3000**. API docs are at **http://localhost:8000/docs**.

### Optional: launch both servers

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run-dev.ps1
```

## Suggested demonstration flow

1. On **Playground**, keep the six Karachi demo points or click the map to add more.
2. Run **Closest pair** with both algorithms. Confirm they agree and compare distance evaluations.
3. Run **Route optimization** with `Exact TSP`, `Nearest neighbour` and `2-Opt` enabled on ≤10 locations.
4. Generate a 40-point synthetic dataset and rerun the closest-pair comparison to see the complexity gap clearly.
5. Switch the route metric to **Road distance (OSRM)** on ≤25 locations to see real road-network costs and geometry.
6. Open **Benchmarks** and run the closest-pair and route suites. Use **Operations** to see distance-evaluation growth.
7. Download a benchmark CSV from the benchmark panels.

## Configuration

All settings have sensible defaults and can be overridden with environment variables.

| Variable | Default | Purpose |
| --- | --- | --- |
| `GEOROUTE_ENGINE_PATH` | auto | Explicit path to the compiled C++ library |
| `GEOROUTE_MAX_CLOSEST_POINTS` | `10000` | Closest-pair request/benchmark cap |
| `GEOROUTE_MAX_EXACT_LOCATIONS` | `10` | Exact TSP input guard |
| `GEOROUTE_MAX_NN_LOCATIONS` | `250` | Heuristic routing cap |
| `GEOROUTE_MAX_OSRM_LOCATIONS` | `25` | Road-matrix request cap |
| `GEOROUTE_OSRM_BASE_URL` | `https://router.project-osrm.org` | OSRM-compatible service |
| `GEOROUTE_OSRM_PROFILE` | `driving` | OSRM routing profile |
| `GEOROUTE_OSRM_TIMEOUT` | `12` | Request timeout in seconds |
| `GEOROUTE_OSRM_CACHE_TTL` | `900` | OSRM response cache lifetime |
| `GEOROUTE_CORS_ORIGINS` | localhost:3000,127.0.0.1:3000 | Allowed browser origins |
| `NEXT_PUBLIC_API_URL` | `http://localhost:8000` | Backend URL used by the frontend |

## API overview

| Method | Endpoint | Description |
| --- | --- | --- |
| GET | `/api/health` | Engine mode, version, limits, routing config |
| POST | `/api/datasets/synthetic` | Generate a deterministic Karachi dataset |
| POST | `/api/datasets/import` | Import a CSV with `lat,lng,name` columns |
| GET | `/api/datasets` | List in-memory datasets |
| GET | `/api/datasets/{id}` | Retrieve one dataset |
| POST | `/api/closest-pair` | Run one or both closest-pair algorithms |
| POST | `/api/route/optimize` | Build a matrix and run selected tour algorithms |
| POST | `/api/benchmarks/closest-pair` | Closest-pair scaling experiment |
| POST | `/api/benchmarks/route` | Route scaling experiment |
| POST | `/api/reports/export` | Export CSV, Markdown or JSON |

See [`docs/API.md`](docs/API.md) for request/response details.

## Testing

```powershell
# C++ engine build + native tests
powershell -ExecutionPolicy Bypass -File .\scripts\build-engine.ps1

# Backend unit + API tests
cd backend
python -m unittest discover -s tests -v

# Frontend type check + production build
cd frontend
npm run typecheck
npm run build

# Everything
powershell -ExecutionPolicy Bypass -File .\scripts\run-tests.ps1
```

The tests cover projection/haversine behaviour, both closest-pair implementations (including cross-boundary and duplicate cases), exact/heuristic TSP validity, API validation, benchmark endpoints and report export.
